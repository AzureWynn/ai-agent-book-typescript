> 对应《AI Agent 开发实战》第 1 章。本章公式：**Agent = LLM + 上下文 + 工具**。

## 一、本章一句话

**Agent 不是"更聪明的模型"，而是"模型 + 上下文 + 工具"的组装——工程（Harness）才是竞争力。**

## 三、贯穿全章的主线：工具调用协议

五个实验是**同一件事的层层递进**：

```
1-0 手写协议：模型请求（tool_calls）→ 你的代码执行
1-1 框架封装：LangChain 把上面封装好 + 消融验证能力来源
1-2 搜索工具：工具从"确定性"变成"外部数据源"
1-3 托管工具：执行权从"你的代码"移到"服务端"，返回类型化记录
1-4 工作流：工具链（改写→生图）的节点编排
```

**底层协议没变过**：请求带 `tools` 描述 → 响应 `tool_calls` → 执行 → 回填 `role: tool` + `tool_call_id` → 循环。

## 四、核心知识点提炼

### 1. ReAct 循环（思考-行动-观察）

```
循环直到 maxIterations:
  思考 → 行动（调工具）→ 观察（看结果）→ 再思考 ...
```

这是全书所有 Agent 的地基，后续每章都是它的变体。**终止条件必须硬编码闸门**（maxIterations），否则模型可能无限循环。

### 2. "完成" ≠ "答对"（评估思维，1-1 最重要的一课）

回答质量要分维度看：有没有终止回复（completed）、数字有没有依据（grounding）、数值对不对（rubric）。**答案要能溯源**——工具结果必须真正喂回模型，隐藏结果 = 逼模型编造。

### 3. 工具是模型与环境之间的接口

- 工具解决模型两大短板：**知识时效性**（搜索工具）和**计算可靠性**（计算器/代码解释器）
- 工具结果必须**格式化压缩**再喂给模型，否则撑爆上下文
- `tool_call_id` 回填是所有多轮工具的通用规则

### 4. 自写工具 vs 托管工具

| | 自写工具（1-0/1-1/1-2） | 托管工具（1-3） |
|---|---|---|
| 模型返回 | `tool_calls`「请求」 | `web_search_call`「已完成记录」 |
| 执行位置 | 你的代码 | 服务端（对 Agent 不透明） |
| 结果 | 文本 | 类型化记录 + 引用（citations） |
| 验收 | 看轨迹 | 看类型化记录是否存在 |

**类型化记录让验收可程序化**：`code_interpreter_call` 存在 = 真用了代码，不看模型文字。

### 5. 协议层 vs 模型层

```
协议层决定"工具能不能用"（代码保证，稳定可靠）
模型层决定"模型会不会用好工具"（依赖模型能力，不可控）
```

工具越强，模型越需要好的编排能力（Model as Agent）。弱模型会反复搜索不推进——这不是协议 bug，是模型局限。

### 6. Skill（技能包）与 Tool 的区别

Tool 给"能力"，Skill 给"方法论"。Skill = SKILL.md + 可选专属工具 + 数据文件，可插拔、按需加载、运行时授权（allowed-tools）。**模型的能力是可插拔的。**

## 五、工程实践启示

1. **先徒手实现一遍协议**，再上框架——理解"框架只是封装，不是魔法"
2. **评估先于优化**：任何"能力提升"都要先定义怎么度量（维度拆解）
3. **设计可插拔接口**：生图/搜索后端可替换，流程代码不动
4. **诚实记录负结果**：本地模型编排失败（1-3 scenario-asean）是真实观察，如实记录比美化更有价值
5. **仿真先行**：本地仿真协议（1-3）换真实 API 时协议层几乎不用改——协议先行是工程红利

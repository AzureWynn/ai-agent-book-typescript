# Chapter 3-5：稀疏向量检索 BM25 · 学习笔记（大白话版）

## 一、这个实验在干什么？

一句话：**查关键词，按"词的重要程度"给文档排序。**

搜索"XK9-2B4-7Q1"，你希望含这个编码的文档排第一。搜索"产品"，含"产品"的文档太多，需要按相关度排序。BM25 就是干这个的：给每个词打分，加起来就是文档得分。

```
查询：model distillation

doc_0 含 model×2、distillation×1  →  4.53 分（命中）
doc_6 含 model×1                  →  也有分，但更低
其他文档一个词都不含              →  0 分（不返回）
```

## 二、倒排索引是什么？

正排是"文档 → 含哪些词"，倒排反过来：**"词 → 出现在哪些文档"**。

```
正排：
  doc_0 → [model, distillation, teacher, ...]
  doc_2 → [xk9-2b4-7q1, warehouse, ...]

倒排：
  model         → {doc_0: tf=2}
  distillation  → {doc_0: tf=1}
  xk9-2b4-7q1   → {doc_2: tf=2}
```

查询时只看查询词的倒排表，不用扫描全部文档。`posting("model")` 直接告诉你谁含这个词、出现了几次。

## 三、TF / IDF / 文档长度

BM25 得分由三部分组成：

```
1. TF（词频）：这个词在这篇文档里出现越多次，越相关
   但要"饱和"：出现 10 次不应该是 1 次的 10 倍分

2. IDF（逆文档频率）：越稀有的词，区分度越高
   "的"几乎每篇都有 → IDF 接近 0
   "XK9-2B4-7Q1"只有一篇有 → IDF 很高

3. 文档长度归一化：长文档天然含词多，要打折
   同样出现 2 次，在短文档里更说明问题
```

公式（单个词对单篇文档的贡献）：

```
score = IDF × (tf × (k1+1)) / (tf + k1 × (1-b + b×|D|/avgdl))
```

- `k1`（默认 1.5）：控制 TF 饱和速度，越大越接近线性
- `b`（默认 0.75）：控制长度归一化强度，0 表示不归一化，1 表示完全归一化

## 四、IDF 为什么长这样？

```
IDF = ln(1 + (N - df + 0.5) / (df + 0.5))
```

- `N`：文档总数，`df`：含这个词的文档数
- 稀有词（df 小）→ 分子大 → IDF 大
- 常见词（df 接近 N）→ 分子小 → IDF 小
- `+0.5` 是平滑，避免除零；外层 `+1` 保证 IDF 非负

实测（10 篇语料）：`model` 只在 1 篇出现，`idf=1.9924`；如果一个词 10 篇全有，IDF 会接近 0，几乎不贡献分数。

## 五、分词决定上限

BM25 只认识"词"，分词错了后面全错。本实验的分词处理：

```
邮箱        user@example.com → 整体保留
十六进制    0x1234 / #FF5733 → 整体保留
产品编码    XK9-2B4-7Q1 → 整体保留（小写）
版本号      2.0.1 → 整体保留
技术术语    C++ → cpp，.NET → dotnet，Node.js → nodejs
字母数字    Python3 / ES6 → 整体保留
停用词      the/is/of → 直接丢掉
```

`--explain` 可以看到查询被切成了什么：`"HTTP 404 error"` → `[http, 404, error]`，`"XK9-2B4-7Q1"` → `[xk9-2b4-7q1]`。

## 六、怎么评测？

和 3-4 一样的三个指标：

| 指标 | 含义 |
|------|------|
| recall@k | 相关文档被找回的比例 |
| precision@k | 返回结果里相关的比例 |
| MRR | 第一个相关结果排名的倒数 |

本实验内置 5 个标注查询，`npm run eval` 实测：

```
model distillation   recall=1.00（精确关键词，稳命中）
HTTP 404 error       recall=1.00（错误码，稳命中）
XK9-2B4-7Q1          recall=1.00（专有编码，稳命中）
BM25 ranking function recall=1.00（术语，稳命中）
cat                  recall=0.00（同义词，漏召回）
宏平均 recall=0.800，MRR=0.800，漏召回率=0.200
```

## 七、同义词短板

这是 BM25 的固有边界，不是 bug：

```
doc_4 只写 kitten，doc_5 只写 feline
查询 cat → 分词得 [cat] → 倒排表里没有 cat → 0 结果
```

稠密检索（3-4）能解决这个问题，因为向量认识"意思相近"。但反过来，搜错误码、产品编码时，BM25 往往比稠密检索更可靠——这就是 3-6 混合检索的动机。

## 八、本实验怎么跑

```bash
npm run demo      # 默认查询 + 同义词漏召回演示 + 索引结构
npm run explain   # 逐词 TF/IDF/贡献（--query 可换词）
npm run eval      # 5 个标注查询的 recall/precision/MRR
```

调参：

```bash
npx tsx src/main.ts --mode eval --k1 2.0 --b 0.5
npx tsx src/main.ts --mode explain --query "HTTP 404 error"
```

## 九、关键洞察

1. **稀有词决定排序**——IDF 让"XK9-2B4-7Q1"这种词一出现就锁定文档
2. **TF 要饱和**——k1 防止"刷词"作弊，出现 10 次不会得 10 倍分
3. **长文档要打折**——b 参数保证短文档不吃亏
4. **分词是隐形上限**——编码、版本号、技术术语切错了，IDF 再准也没用
5. **BM25 和稠密检索互补**——精确词用 BM25，同义表达用稠密，3-6 把它们拼起来

## 十、常见问题

- **查同义词没结果**：正常，这是词面匹配的边界，不是程序故障
- **precision@5 只有 0.20**：正常——每个查询只有 1 篇相关，top-5 里 1/5=0.20；看 recall 和 MRR 更有意义
- **改 k1/b 没变化**：语料太小（10 篇）时参数影响不明显；重点看 `--explain` 的分项贡献
- **大小写查不到**：分词已统一小写，查询大小写不敏感
- **想加中文**：当前分词面向英文/代码场景，中文需要额外分词器

# Chapter 3-4：稠密嵌入向量检索 · 学习笔记（大白话版）

## 一、这个实验在干什么？

一句话：**把文字变成向量，然后找出"意思最接近"的那几条。**

想象你有一个知识库，里面有几千条文档。用户问"怎么让模型收敛更快"，你希望找到最相关的几条文档。问题是：用户不会用文档里的原词——文档写的是"优化器学习率调度"，用户说的是"收敛更快"。关键词搜索（BM25）就懵了。

稠密检索的做法：

```
文字  →  [嵌入模型]  →  一串数字（向量）
                          [0.12, -0.45, 0.78, ...]

两段文字意思接近  →  它们的向量在空间里距离近
```

这个实验做两件事：
1. 用嵌入模型把文本编码成向量
2. 用**近似最近邻（ANN）**算法快速找到最近的向量

## 二、为什么需要"近似"搜索？

最笨的办法是**暴力搜索**（brute force / exact search）：拿查询向量，和库里每一个向量都算一次距离，排序取前 k 个。

- 优点：100% 准确
- 缺点：库有 100 万条，每次查询要算 100 万次距离，太慢

**ANN（近似最近邻）**的思路：牺牲一点点准确率，换取快得多的速度。

```
暴力搜索：查 100 万次 → 10ms，召回 100%
ANN 搜索：查 1000 次  → 0.1ms，召回 95%
```

关键问题：**牺牲多少准确率，换多少速度？** 这就是本实验要观察的。

## 三、两种 ANN 算法

### ANNOY（树结构）

ANNOY = **A**pproximate **N**earest **N**eighbors **O**h **Y**eah（名字是认真的）

原理：把空间用**随机超平面**不断切分，建成一棵或多棵二叉树。

```
        [全部向量]
        /        \
   左半边        右半边
   /    \        /    \
 ...    ...    ...    ...
```

查询时：从根往下走，只访问可能包含近邻的叶子。

```
特点：
  • 建索引快
  • 内存占用低
  • n_trees 越大越准（但也越慢）
  • ❌ 不能删除/更新，只能重建
  • 适合：静态数据、读多写少
```

### HNSW（图结构）

HNSW = **H**ierarchical **N**avigable **S**mall **W**orld（分层可导航小世界图）

原理：建一张**多层图**，上层稀疏（快速跳转），下层密集（精确定位）。

```
第 2 层（最稀疏）：  A ———————— F
                     \        /
第 1 层（中等）：  A — B — D — F — G
                   |   |   |   |
第 0 层（最密集）： A-B-C-D-E-F-G-H-I...
```

查询时：从顶层入口点开始，逐层往下"贪婪搜索"，快速逼近目标。

```
特点：
  • 召回率高
  • 支持增量添加 + 软删除
  • 内存占用更高、建索引更慢
  • M / ef_search 越大越准（但也越慢）
  • 适合：动态数据、需要频繁更新
```

## 四、怎么衡量好坏？

### 召回率 recall@k

**ANN 找到的 top-k，有多少条出现在暴力搜索的 top-k 里？**

```
暴力搜索 top-10 = {A, B, C, D, E, F, G, H, I, J}
ANN   搜索 top-10 = {A, B, C, D, E, X, Y, Z, W, V}

recall@10 = 5 / 10 = 50%
```

召回率 100% 表示 ANN 和暴力搜索结果完全一致。**注意：召回率高不代表结果对用户有用**——那是嵌入模型的质量问题，不是索引的问题。

### 其他指标

| 指标 | 含义 |
|------|------|
| precision@k | top-k 里有多少是真正相关的 |
| MRR | 第一个相关结果排名的倒数（越接近 1 越好） |
| 建索引耗时 | 一次性成本 |
| 查询延迟 | 每次查询的成本 |
| 内存占用 | 索引占多少内存 |

## 五、表示误差 vs 近似搜索误差

这是本实验最容易混淆、也最重要的区分：

```
┌─────────────────────────────────────────────────┐
│  第一层：表示（嵌入模型）                          │
│  文本 → 向量，这一步就有误差                       │
│  • 意思相近但向量不近 → 漏掉（模型不好）           │
│  • 意思不同但向量很近 → 误召回（模型不好）         │
├─────────────────────────────────────────────────┤
│  第二层：搜索（ANN 索引）                          │
│  在向量集合里找最近邻，这一步也有误差               │
│  • 真正的最近邻没被找到 → 召回损失（索引不好）     │
└─────────────────────────────────────────────────┘
```

**即使暴力搜索找到了距离最近的向量，那条文档也未必是最佳答案**——这属于表示与任务目标之间的差别。

所以分析 ANN 对比时，要分开看：
1. 近似搜索相对精确搜索的召回（索引质量）
2. 最终结果对原问题是否有用（表示质量）

## 六、本实验怎么跑

```bash
npm run demo      # 单条查询，对比精确/ANNOY/HNSW
npm run compare   # 多查询统计：建索引耗时、查询延迟、召回率
npm run sweep     # 参数扫描：n_trees / ef_search 对召回的影响
```

```
1. createTestDocuments()     生成测试语料
2. buildDocumentEmbeddings() 批量嵌入

6. searchAnnoy/searchHnsw()  对比召回率
```

## 八、参数怎么调

### ANNOY：n_trees

| n_trees | 建索引 | 召回 | 内存 |
|---------|--------|------|------|
| 1 | 最快 | 最低 | 最低 |
| 10 | 中等 | 中等 | 中等 |
| 50 | 较慢 | 较高 | 较高 |

### HNSW：M 和 ef_search

| 参数 | 作用 | 增大后果 |
|------|------|----------|
| M | 每个节点的连接数 | 召回↑、内存↑、建索引↑ |
| ef_construction | 建索引时的候选集大小 | 召回↑、建索引↑ |
| ef_search | 查询时的候选集大小 | 召回↑、查询↑ |

## 九、关键洞察

1. **稠密检索解决了"词不同、意思同"的问题**——这是相对 BM25 稀疏检索的核心优势
2. **ANN 是速度与召回的权衡**——没有免费的午餐，参数决定落在哪一点
3. **ANNOY 和 HNSW 各有适用场景**——静态数据用 ANNOY，动态数据用 HNSW
4. **召回率和答案质量是两回事**——索引召回 100%，答案也可能不相关（表示问题）
5. **参数扫描比单点测试更有说服力**——能看到召回随参数变化的趋势

## 十、常见问题

- **Ollama 没启动**：`npm run demo` 会报连接错误，先 `ollama serve`
- **模型没下载**：`ollama pull nomic-embed-text`
- **召回率总是 100%**：语料太小或太同质，ANN 轻松找到所有近邻；增大语料或调低参数
- **ANNOY 在 macOS/arm64 上不稳定**：部分预编译轮子有缺陷，HNSW 不受影响
- **换嵌入模型后维度变了**：向量维度必须一致，否则索引报错

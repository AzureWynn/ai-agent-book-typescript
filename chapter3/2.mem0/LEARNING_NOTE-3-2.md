# Chapter 3-2：开源记忆框架对比 · 学习笔记（大白话版）

## 一、两个框架在干什么？

3-1 我们自己实现了一个记忆系统。3-2 看看别人是怎么做的——用两个开源框架：

| | mem0 | memobase |
|---|---|---|
| **核心思路** | ADD-only：只加不减 | 四类记忆 + 画像/事件分离 |
| **检索方式** | 语义 + BM25 混合 | 按类型检索 + 聚类压缩 |
| **评测** | LOCOMO 基准 | LOCOMO 基准 |
| **后端** | ChromaDB / 云端 | pickle 文件 / 服务端 |
| **适合谁** | 想要快速接入成熟框架 | 想要理解记忆系统内部机制 |

## 二、mem0：只加不减的魔法

### 大白话

```
mem0 就像一个"只进不出的冰箱"：

1. 聊天时，模型自动判断哪些信息值得记住
2. 值得记住的 → 直接存入（ADD）
3. 不需要删除、不需要修改（ADD-only）
4. 查记忆时 → 语义搜索 + 关键词搜索一起用
```

### 核心概念

| 概念 | 大白话 | 例子 |
|------|--------|------|
| ADD-only | 永远只新增，不改旧的 | 第一次记"喜欢火锅"，第二次不会覆盖它 |
| Entity Filter | 按用户隔离记忆 | Alice 的记忆不会混入 Bob 的 |
| Hybrid Search | 语义 + 关键词双保险 | 搜"火锅"能匹配"喜欢吃火锅"和"辣味食物" |
| LOCOMO | 评测基准 | 测试记忆系统在长对话中表现如何 |

```
mem0 的记忆流程：

  用户说："我刚换了新工作"
       ↓
  mem0 框架自动判断：这条信息重要吗？
       ↓
  是 → ADD 进去（只加不改）
       ↓
  存储：ChromaDB 向量数据库
       ↓
  下次搜索：语义匹配 + BM25 关键词匹配
       ↓
  返回相关记忆给模型
```

### 为什么 ADD-only？

```
传统方式：
  记"喜欢火锅" → 后来改成"喜欢日料" → 需要 update/delete
  问题：改的时候可能搞丢其他信息

ADD-only：
  记"喜欢火锅" → 后来改"喜欢日料" → 新增"喜欢日料"
  好处：不会丢失任何信息，所有记忆都保留
  检索时按重要性排序，重要的在前面
```

## 三、memobase：四类记忆 + 画像/事件

### 大白话

```
memobase 把记忆分成 4 种类型，就像整理衣柜：

  📁 情景记忆（Episodic）：发生了什么
     → "昨天吃了火锅"
     
  📁 语义记忆（Semantic）：事实和概念
     → "火锅是一种烹饪方式"
     
  📁 程序记忆（Procedural）：怎么做
     → "切火锅食材的方法"
     
  📁 工作记忆（Working）：当前任务相关
     → "正在为火锅派对做准备"
```

### Profile + Event 双模型

```
Profile（画像）：
  相对稳定的属性
  → 用户 Alice，女，30 岁，喜欢日料
  → 不常变化

Event（事件）：
  随时间变化的具体经历
  → 2025-09-22 吃了火锅
  → 2025-09-23 换了新工作
  → 有时间戳
```

### 核心机制

| 机制 | 大白话 | 为什么需要 |
|------|--------|-----------|
| **重要性衰减** | 旧记忆逐渐变不重要 | 新信息比旧信息更相关 |
| **聚类压缩** | 相关记忆合并成摘要 | 减少记忆数量 |
| **超阈值压缩** | 太多相似记忆时合并 | 防止记忆膨胀 |
| **近因检索** | 优先返回最近的记忆 | 最近的信息更有用 |

```
memobase 的记忆生命周期：

  添加记忆
    ↓
  计算 importance_score（初始 1.0）
    ↓
  每次访问 → importance_score * 1.1（越用越重要）
    ↓
  每隔一段时间 → importance_score *= (1 - decay_rate)（自然衰减）
    ↓
  超过阈值 → 聚类压缩成摘要
    ↓
  检索时 → 按 importance 排序，返回 Top-K
```

## 四、两个框架对比

### 设计哲学

```
mem0：简单即美德
  ┌─────────────────────────────────────────────┐
  │  • 只加不减 → 永远不会丢信息                  │
  │  • 混合检索 → 语义 + 关键词双保险            │
  │  • 接入简单 → 一个 Memory 对象搞定一切      │
  │  • 成熟稳定 → 有 LOCOMO 评测背书              │
  └─────────────────────────────────────────────┘

memobase：精细化管理
  ┌─────────────────────────────────────────────┐
  │  • 四类记忆 → 区分不同性质的信息             │
  │  • 画像/事件分离 → 稳定属性和时间线分开      │
  │  • 衰减/聚类 → 自动管理记忆生命周期          │
  │  • 可扩展 → 支持自定义记忆类型               │
  └─────────────────────────────────────────────┘
```

### 关键差异

| 维度 | mem0 | memobase |
|------|------|----------|
| **写入策略** | ADD-only（只加） | 按类型添加 + 压缩 |
| **修改策略** | 不修改旧记忆 | 重要性衰减自动"软删除" |
| **检索方式** | 语义 + BM25 混合 | 按类型 + 重要性排序 |
| **存储后端** | ChromaDB / 云端 | pickle / Memobase 服务 |
| **复杂度** | 低（接入简单） | 高（内部机制丰富） |
| **适用场景** | 快速集成 | 深度定制 |

### 与 3-1 自实现的对比

```
3-1 自实现：
  • notes/enhanced_notes/json_cards/advanced_json_cards
  • 手动调用 add/update/delete
  • JSON 文件存储
  • 适合学习原理

mem0：
  • ADD-only 自动提取
  • 向量数据库存储
  • 适合生产环境快速接入

memobase：
  • 四类记忆自动管理
  • 重要性衰减 + 聚类压缩
  • 适合需要精细控制的场景
```

## 五、核心结论

1. **没有银弹** — mem0 适合快速接入，memobase 适合精细控制
2. **ADD-only 是趋势** — 避免丢失信息，检索时按重要性排序
3. **记忆需要分类** — 稳定属性（Profile）和事件经历（Event）应该分开
4. **衰减是必要的** — 旧信息不应永久占据重要位置
5. **3-1 是基础** — 理解了 3-1 的原理，才能理解框架做了什么

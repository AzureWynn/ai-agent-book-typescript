# Chapter 3-10：上下文感知检索 · 学习笔记（大白话版）

## 一、这个实验在干什么？

一句话：**分块把上下文切丢了，索引前给每块补一句"我是谁、从哪来"。**

```
原文（b2 块）："上述扣除标准自明年一月起执行。"
查询："赡养老人扣除标准何时执行"

块里没有"赡养""老人"，只有"扣除标准"——检索靠猜。
补上前缀："本块属于个人所得税赡养老人专项附加扣除，每月三千元。"
查询词全有了，排名第一。
```

Anthropic 把这叫 Contextual Retrieval：每个分块配一段专属背景（2-3 句），`前缀 + 原文`一起索引。

## 二、什么是"孤儿分块"？

指代词和省略把块和全文的联系切断了：

```
a2："该政策于次年生效。"——哪个政策？哪一年？
b2："上述扣除标准自明年一月起执行。"——什么扣除？
c2："该职权不受行政机关干涉。"——什么职权？
d2："其中云业务增长20%。"——哪家公司？
```

人读着全文能懂，检索只看到孤块就懵了。前缀就是把"人读全文才知道的"提前写进块里。

## 三、前缀里写什么？

只写**定位信息**，不写答案：

```
好前缀（a2）："本块属于2023年发布的新能源汽车购置税减免政策说明。"
  → 文档名 + 主题，查询词能对上

坏前缀："本块说政策次年生效，有效期三年。"
  → 只是复述原文，加了等于没加

危险前缀："本块回答何时生效：次年，即2024年。"
  → 把答案（或推断）写进去了，召回虚高
```

检查题（官方原话精神）：前缀加入了原文没有的信息，即使提高召回，是否仍应保留？答案：删掉重写。

## 四、实测怎么读？

`npm run compare`（12 块语料，8 查询，BM25）：

```
                recall@1    recall@3    recall@5
无前缀 plain      75.0%      100.0%      100.0%
有前缀 ctx       100.0%      100.0%      100.0%
提升              +25.0pp     +0.0pp      +0.0pp
失败率下降(@1)    100%
```

读法：
- 增益全部集中在 top-1：前缀解决的是"排第一还是排第二"，不是"找得到找不到"
- 6 个查询本来就 top-1 命中（块里词够用）；2 个孤儿块（a2、d2）被前缀从第 2 推到第 1
- 官方大语料上是 60%→86.7%（+26.7pp，失败率降 67%）；小语料上是 75%→100%——形状一致
- recall@3/5 打平：前缀不扩大召回集合，只改变排序

## 五、前缀是 LLM 生成的吗？

生产里是：把全文（或周边）+ 目标块喂给 LLM，让它写 2-3 句定位。本实验默认用**手写前缀**（离线、确定、可审查），`--llm-prefix` 开关调 gemma4 现场生成：

```bash
npx tsx src/main.ts --mode demo --llm-prefix --query "天翼科技云业务增长多少"
```

对比两者：模型写的前缀和手写的前缀，谁定位信息更准？谁混入了多余推断？这本身就是一道练习题。

## 六、本实验怎么跑

```bash
npm run demo       # 前 3 个查询的 plain/ctx 逐路对比
npm run compare    # recall@1/3/5 对比表 + 失败率下降
npx tsx src/main.ts --per-query   # 逐查询排名，标出被前缀修复的
```

换查询：

```bash
npx tsx src/main.ts --mode demo --query "国家主席有哪些职权"
npx tsx src/main.ts --mode demo --query "扣除方式有哪些" --top-k 3
```

## 七、核心代码结构

```
src/
├── tokenizer.ts   # 中文按字 + ASCII 按词（与 3-8/3-9 同规则）
├── index.ts       # BM25（与 3-5~3-9 同规则）
├── corpus.ts      # 12 块（4 孤儿标出）+ 手写前缀 + 8 个标注查询
├── prefix.ts      # handPrefix + contextualText + gemma4 现场生成
├── compare.ts     # 双索引构建 + recall@k + 失败率下降
└── main.ts        # CLI（demo / compare / per-query / llm-prefix）
```

关键设计：同一批块建**两个**索引（plain 只用原文，ctx 用前缀+原文），查询集合完全相同——唯一变量就是前缀，增益归因干净。

## 八、成本账

前缀不是免费的，生产要算三笔账：

```
1. 生成成本：每个块调一次 LLM（Anthropic 测过，值得）
2. 索引成本：块变长了，索引变大、检索变慢一点
3. 失真风险：前缀写错或泄题，召回数字好看但答案错了
```

本实验只量化第 0 步（召回增益）；评估完整流程还要加上这三笔。

## 九、关键洞察

1. **前缀解决的是排序，不是召回**——增益集中在 top-1，@3/@5 经常打平
2. **只写定位，不写答案**——混入答案的召回是虚的
3. **对照实验要干净**——同语料、同查询、双索引，唯一变量是前缀
4. **孤儿块是分块的原罪**——指代和省略专切长文档，越长的文档越需要前缀
5. **手写前缀是上限参考**——LLM 生成的前缀能接近手写质量，才算合格

## 十、常见问题

- **提升只有 top-1**：正常，这正是该方法的标准形状（官方也一样）
- **某查询本来就第一**：正常，块里词够用就不需要前缀；看 `--per-query` 找被修复的那两条
- **`--llm-prefix` 很慢**：每个块一次 LLM 调用；先在小语料上试
- **模型前缀混入推断**：删掉重写，或收紧 prompt（"只写定位信息"）
- **和 3-9 的 enrichment 头区别**：3-9 的头是结构化元数据（会话/轮次），这里是自然语言背景；一个管"哪来的"，一个管"讲什么的"

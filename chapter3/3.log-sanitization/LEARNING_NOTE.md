# Chapter 3-3：日志脱敏 · 学习笔记（大白话版）

## 一、这个实验在干什么？

一句话：**把 Agent 日志里的敏感信息藏起来，但让其他内容还能看懂。**

想象这个场景：Agent 跑了很久，生成了大量日志。你想用日志排查问题，但日志里可能包含：
- 用户的手机号、身份证号
- API Key、数据库密码
- 信用卡号

直接展示日志=泄露隐私。全部打码=没法排查问题。

日志脱敏的目标：**只替换敏感字段，保留上下文。**

```
原始日志：
  "User 13800138000 called with API key sk-abc123..."

脱敏后：
  "User [REDACTED_PHONE] called with API key [REDACTED_API_KEY]..."
```

```
└─────────────────────────────────────────────────┘
```

## 三、18 类敏感信息

| 大类 | 具体内容 | 例子 |
|------|----------|------|
| **密钥类** | API Key、AWS Key、GitHub Token、Slack Token、JWT、Bearer Token | `sk-...`, `AKIA...`, `ghp_...` |
| **认证类** | Basic Auth、URL 密码、密码赋值 | `Authorization: Basic ...` |
| **PII** | 手机号、身份证、邮箱、信用卡、SSN | `13800138000`, `110101...` |
| **其他** | IP 地址、IBAN、私钥 | `192.168.1.1` |

## 四、核心技术点

### 正则 + 校验

```
不是所有匹配都是真正的敏感信息：
  • "4532 1234 5678 9012" 可能是信用卡，也可能是随机数
  • 用 Luhn 算法验证 → 通过才是信用卡
  • "110101199003071234" 可能是身份证，也可能是其他数字
  • 用身份证校验码验证 → 通过才是身份证
```

### 校验算法

```
Luhn 校验（信用卡）：
  1. 从右到左，偶数位乘 2
  2. 如果 > 9 减 9
  3. 所有位相加
  4. 总和 % 10 == 0 → 有效

身份证校验码（中国）：
  1. 前 17 位 × 权重 [7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]
  2. 总和 % 11
  3. 对应校验码表 [1,0,X,9,8,7,6,5,4,3,2]
  4. 匹配最后一位 → 有效
```

## 五、为什么重要？

```
没脱敏的后果：
  • 日志发到监控平台 → 所有人看到 API Key
  • 团队共享日志 → 用户隐私泄露
  • 合规审计 → 违反 GDPR/个人信息保护法

过度脱敏的后果：
  • 把时间戳也打码 → 无法排查问题
  • 把 IP 也打码 → 无法定位故障
  • 脱敏太多 → 日志失去价值

平衡：只替换敏感字段，保留一切有用的上下文。
```

## 六、大白话总结

```
日志脱敏的生命周期：

  Agent 运行产生日志
       ↓
  检测敏感信息（正则匹配）
       ↓
  验证是否真的是敏感信息（Luhn/身份证校验）
       ↓
  替换为 [REDACTED_xxx] 占位符
       ↓
  保留上下文（"User [REDACTED_PHONE] called"）
       ↓
  安全的日志 → 可以放心分享
```

## 九、关键结论

1. **规则引擎是第一道防线** — 快速、确定、不依赖模型
2. **校验很重要** — 不是所有匹配都是真正的敏感信息
3. **只脱敏敏感的** — 保留上下文，不要过度脱敏
4. **占位符要带类别** — `[REDACTED_API_KEY]` 比 `[REDACTED]` 更有用

# Chapter 3-8：Agentic RAG · 学习笔记（大白话版）

## 一、这个实验在干什么？

一句话：**问题越复杂，一次检索越不够，Agent 要分几轮找齐证据。**

```
简单题："醉酒驾驶机动车如何处罚"
  → 一次检索就找全（答案只在一处）

复杂题："醉酒驾车致人重伤，且有盗窃前科，怎么量刑"
  → 需要三块证据：醉驾处罚 + 过失重伤 + 累犯从重
  → 一次检索只能找全其中两块
  → Agent 发现缺了"累犯"，再查一轮，补齐
```

Non-Agentic RAG：查一次，答一次。
Agentic RAG：查 → 看缺什么 → 再查 → 查全了才答（ReAct 循环）。

## 二、证据召回率是什么？

本实验的指标不是"答得好不好"，而是**"该找的法条找齐了没有"**：

```
evidence recall = 找回的相关法条 / 应该找回的法条
```

它是答案质量的上界：证据都没找齐，答案不可能对；证据找齐了，答案才可能对。先把检索方法练对，再谈生成质量。

## 三、Agent 的循环长什么样？

```
第 1 轮：用原问题查
  命中：醉驾、过失重伤
  缺口：累犯 ← 模型发现"前科"还没着落
第 2 轮：针对缺口查"累犯从重处罚"
  命中：累犯
  缺口：无 → 停止
```

实测追踪（`npm run demo`）：

```
round 1 query="醉酒驾车致人重伤，且有盗窃前科，怎么量刑"
  hits=[c_drunk, c_negligent, c_hurt]  missing=[累犯]
round 2 query="醉酒驾驶处罚"
  hits=[c_recidivist, ...]  missing=[(none)]  → 停止
evidence recall: 0.67 → 1.00
```

关键规则只有一条：**新检索必须填补明确的证据缺口；缺口补完就停**。没有停止条件，Agent 会反复查同一内容。

## 四、简单题为什么不用多轮？

```
"故意伤害致人重伤的，如何处罚"
round 1：hits=[c_hurt, ...]  missing=[(none)]  → 直接停止
retrievals = 1 → 1
```

多检索几次不自动更好：重复查询浪费时间，还可能引入无关片段干扰答案。Agent 的价值在于**该查才查**，简单题 1 轮，复杂题 2~3 轮。

## 五、中文分词怎么做？

英文按词切，中文按字切（unigram）+ ASCII 词：

```
"醉酒驾驶机动车如何处罚"
→ [醉, 酒, 驾, 驶, 机, 动, 车, 如, 何, 处, 罚]
   （的/如何/怎么 等停用字丢掉）
```

字级别 BM25 对短法条够用：查询和法条共享的字越多，得分越高。`XK9` 这类 ASCII 编码走英文规则整体保留。

## 六、实测怎么读？

`npm run eval`（12 篇法条，8 个问题，top-3）：

```
easy ×3   single=100%  decomposed=100%  检索 1→1
hard ×5   single=87%   decomposed=100%
  其中两道 3 要素题：67% → 100%，检索 1→2
```

读法：
- 简单题打平：证据只在一处，分解检索纯属多余
- 差距集中在最难的题：要素越多，单次检索的固定预算越不够分
- 分解检索把预算花在每个缺口上：一个要素一次检索
- 官方大语料上是 8%→100%；小语料上是 87%→100%——趋势一致，幅度随语料规模变化

## 七、本实验怎么跑

```bash
npm run demo      # 一道难题 + 一道简单题的逐轮追踪
npm run eval      # 8 问题 × 单次/分解的证据召回表
npm run answer    # Agentic 取证 → gemma4 生成带引用回答（需 Ollama）
```

换查询（无标注时只展示单次检索）：

```bash
npx tsx src/main.ts --mode demo --query "抢劫如何处罚"
npx tsx src/main.ts --mode eval --top-k 5
npx tsx src/main.ts --mode answer --query "醉酒驾车致人重伤，且有盗窃前科，怎么量刑"
```

`answer` 模式不计入评测：评测只看检索层（证据找齐没有），生成层只看端到端观感，且引用编号要人工核对。

## 八、核心代码结构

```
src/
├── tokenizer.ts   # 中文按字 + ASCII 按词，停用字过滤
├── index.ts       # BM25（与 3-5/3-6/3-7 同规则）
├── corpus.ts      # 12 篇法条（带要素标签）+ 8 个标注问题
├── agent.ts       # singleSearch + runAgentic（缺口驱动循环）
├── metrics.ts     # avg / missRate
└── main.ts        # CLI（demo / eval）
```

`runAgentic` 就是 ReAct 的最小形态：

```
planned = [原问题, ...标注子查询]   # 生产里子查询由模型现场生成
for 每轮：
  检索 → 算已覆盖要素 → 算缺口
  缺口为空 → 停止
```

生产与教学的唯一区别：子查询是模型现场写的，还是预先标好的。本实验用预标注隔离出"检索策略"本身。

## 九、关键洞察

1. **证据召回是答案质量的上界**——先找齐，再答对
2. **复杂 = 多要素**——要素越多，单次检索预算越不够
3. **停止条件和检索同样重要**——缺口补完就停，不多查一轮
4. **简单题不需要 Agent**——1 轮结束才是好 Agent
5. **分解检索的本质是预算分配**——一个缺口一次检索

## 十、常见问题

- **分解全满分**：语料小（12 篇）时正常；看"检索次数 1→2"列和逐轮追踪更有信息
- **某轮 hits 含无关条目**：正常，BM25 按字面匹配；只要相关条目在 top-k 内，召回就不受影响
- **自定义查询无分解**：无标注缺口信息，只能展示单次检索；要玩分解，先给问题标 facets 和 subqueries
- **中文分词太糙**：字 unigram 是教学简化；生产用 jieba/HanLP 或词向量
- **生成答案在哪**：本实验只练检索（证据召回）；端到端回答需要接 LLM，官方用 evaluation/evaluate.py（需 API Key）

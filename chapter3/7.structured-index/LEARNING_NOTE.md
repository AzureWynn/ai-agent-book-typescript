# Chapter 3-7：结构化索引 · 学习笔记（大白话版）

## 一、这个实验在干什么？

一句话：**给文档加"目录"和"关系图"，让检索走结构而不是瞎翻。**

扁平检索（3-4/3-5/3-6）把文档切成互不相干的片段。有两类问题它答不好：

```
1. 多跳问题："运行 ADDPS 前，OS 要置哪个控制位？"
   答案藏在关系里：ADDPS 属于 SSE，SSE 需要 CR4.OSFXSR。
   没有一片文档同时写全这三件事。

2. 综合问题："SSE 用到哪些寄存器？"
   答案散在多片里，需要拼起来。
```

本实验比较两种结构：

```
RAPTOR：把片段逐层聚成摘要，建成一棵树
  叶子 = 原文片段 → 中层 = 主题摘要 → 树根 = 全文总览

GraphRAG：抽实体和关系，建成一张图
  ADDPS --属于--> SSE --需要--> CR4.OSFXSR
  查询沿边走 2 跳，直达答案
```

## 二、RAPTOR 是怎么建的？

```
第 0 层（叶子）：10 个原文片段，原样保留
第 1 层（中层）：3 篇主题摘要
  mid_sse：SSE 家族（ADDPS、XMM、MOV、SSE2）
  mid_sys：系统使能（CR4.OSFXSR、FXSAVE、控制寄存器）
  mid_avx：AVX 演进（VADDPS、YMM）
第 2 层（树根）：全文总览，一段话
```

检索时对**所有节点**打分（叶子和摘要一起比），返回最佳节点并给出 `root → mid → leaf` 路径。一个中层节点命中，等于一次召回它覆盖的全部片段。

生产里的 RAPTOR 用嵌入聚类（GMM）+ LLM 写摘要；本实验手写树结构，保证离线可跑、每一步可解释。

## 三、GraphRAG 是怎么建的？

三步：

```
1. 抽实体：ADDPS、SSE、XMM、CR4.OSFXSR、VADDPS、YMM、AVX、MOV、FXSAVE、CR4
2. 连关系：ADDPS --属于--> SSE，SSE --需要--> CR4.OSFXSR，……
3. 分社区：simd_family / system / avx_line（三坨）
```

查询时：

```
1. 查询词命中实体（"ADDPS" → ADDPS）
2. 从命中实体 BFS 走 2 跳
3. 沿途实体提到的片段按距离加权：1/(dist+1)
```

招牌用例就是那条两跳路径：

```
ADDPS --属于--> SSE --需要--> CR4.OSFXSR
```

## 四、扁平 vs 树 vs 图

| 维度 | 扁平（BM25） | RAPTOR 树 | Graph 图 |
|------|-------------|-----------|----------|
| 组织 | 无，片段独立 | 自顶向下的摘要层级 | 实体关系网 |
| 擅长 | 精确词命中 | 综述、综合、多层定位 | 多跳关系 |
| 构建成本 | 分词+倒排，最低 | 聚类+摘要，中等 | 实体关系抽取，最高 |
| 风险 | 看不懂关系 | 摘要压掉细节 | 关系抽错/排序稀释 |

## 五、实测怎么读？

`npm run eval`（10 篇语料，5 查询，top-3）：

```
Flat    recall=0.800
RAPTOR  recall=1.000
Graph   recall=0.600
```

逐个看才有意思：

```
q1 多跳（ADDPS→控制位）：
  flat=[c_osfxsr, ...]   ✓ 查询词恰好和答案片段重叠，扁平直接命中
  graph 路径正确（ADDPS→SSE→CR4.OSFXSR），但答案排在兄弟节点后面
  → 结构"发现"了连接，朴素距离排序却把它稀释了

q3 综述（Explain SSE）：
  flat=[c_xmm, c_sse2, c_fxsave]  ✗ 全是孤立片段，没有总览
  raptor=[mid 级节点覆盖 c_xmm/c_addps/c_sse]  ✓ 一次命中一片
```

结论不是"谁永远赢"，而是三条：

1. 查询词和答案重叠时，扁平又快又准，不需要结构
2. RAPTOR 赢在综合和总览：一个中层节点一次召回一片
3. 图找到了连接但排不好——**结构不能保证正确，构建质量和排序同样重要**（官方原话精神）

## 七、核心代码结构

```
src/
├── tokenizer.ts   # 分词（与 3-5/3-6 同规则）
├── index.ts       # 通用 BM25 文本索引（扁平和树节点共用）
├── kb.ts          # 手写知识库：10 片段 + 树 + 实体关系 + 标注
├── raptor.ts      # 树检索：全节点打分 + root→leaf 路径 + 覆盖映射
├── graph.ts       # 图检索：实体命中 + 2 跳 BFS + 距离加权
├── metrics.ts     # recall@k / MRR
└── main.ts        # CLI（demo / eval）
```

## 八、两个实现细节

**RAPTOR 覆盖映射**：节点命中后不直接返回节点，而是返回它覆盖的原文片段（`coveredChunks`，中层优先、按分排序）。这样评测才能和扁平/图站在同一标尺上比。

**图的距离加权**：`score = Σ 1/(dist+1)`，查询命中的实体 dist=0，邻居 dist=1，邻居的邻居 dist=2。离查询越近权重越高，2 跳之外直接截断。

## 九、关键洞察

1. **结构是手段，不是正确性本身**——本实验图召回 0.6 就是证明
2. **RAPTOR 的本质是"一次召回一片"**——中层摘要命中等于批量召回
3. **图的本质是"连接即答案"**——路径本身就是解释（ADDPS→SSE→CR4.OSFXSR）
4. **构建质量决定上限**——摘要失真、关系抽错，后面全错；答案必须能回到原文片段
5. **选型看问题类型**——"哪里定义"走扁平/叶子，"有何共性"走树，"A 与 B 如何相连"走图

## 十、常见问题

- **图召回比扁平低**：正常。朴素距离排序会被高扇出稀释；看 `--mode demo` 的路径追踪，连接本身是对的
- **想让图赢**：给边加权、按查询相关性重排子图，或换 LLM 对子图推理（生产 GraphRAG 做法）
- **RAPTOR 全对**：语料小（10 篇）且摘要手写保真；换 LLM 自动摘要要抽查失真
- **中文查询**：当前分词面向英文/代码，中文需要额外分词器
- **生产构建要什么**：RAPTOR 需嵌入+聚类+摘要 LLM；GraphRAG 需实体关系抽取 LLM；本实验手写结构只为教学

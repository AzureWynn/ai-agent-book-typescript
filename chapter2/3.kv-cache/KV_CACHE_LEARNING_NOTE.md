# KV Cache —— 教学笔记

> 本笔记对应实验 2-3（KV Cache 与错误上下文管理模式）。
> 核心目标：**理解为什么"看似无害的小改动"会让模型变慢 2-3 倍。**

---

## 一、这个实验在干什么？

一句话：**证明"怎么问"和"问什么"一样重要。**

大模型推理时，会把中间计算结果缓存起来（KV Cache）。下次对话时，如果前面的内容没变，就可以直接复用缓存，不用重新计算。

这就像你开了一家复印店：客户第一次打印了一份 100 页的合同，你花了 10 分钟复印完并保存。第二次客户要在后面加一页，如果合同前面 99 页没变，你只需要印新的一页（1 分钟）。但如果客户要求把合同格式全部重排一遍，你就得全部重新印（10 分钟）。

**本实验：跑 6 种不同的"问法"，看看哪种最省时。**

---

## 二、什么是 KV Cache？

### 大白话版

模型每生成一个词，都要做大量计算。这些计算结果（Key 和 Value 向量）就是"中间答案"。

KV Cache 就是把这些"中间答案"记在本子上。下一轮对话时，如果前面的问题没变，就可以直接翻本子看答案，不用重新算。

```
第 1 轮: "帮我找文件" → 算了 100 次 → 缓存记下来
第 2 轮: "然后读那个文件" → 只需算新增的 10 次（前面 100 次从缓存取）
```

### 为什么重要？

数据说话：
- 有缓存：首 token 延迟 **0.3 秒**
- 没缓存：首 token 延迟 **5 秒**

差了 **17 倍**。对用户体验来说，这就是"秒开"和"等半天"的区别。

## 三、实验设计：6 种模式，1 正 5 反

实验任务：让 Agent 查找 .ts 文件并总结。6 种模式用同样的任务，但"问法"不同：

### 正确模式（correct）✅

```
系统提示（固定不变）
用户：查找文件
助手：找到了 xxx
用户：读取文件内容
助手：内容如下...
```

**关键：系统提示固定，消息逐轮追加。** 前面的内容永远不变 → 缓存一直命中。

### 反模式 1：dynamic_system ❌

```
系统提示（含当前时间戳）← 每轮都变！
用户：查找文件
...
```

**问题：时间戳每轮不同 → 系统提示变了 → 缓存全部失效。**

大白话：就像复印店每天换个新合同模板，客户每次来都要重印全部。

### 反模式 2：shuffled_tools ❌

```
工具列表：[read_file, find]    ← 顺序 A
下一轮：[find, read_file]       ← 顺序 B，变了！
```

**问题：工具顺序变了 → prompt 模板变了 → 缓存失效。**

大白话：就像菜单把"前菜"和"主菜"顺序对调了，厨房得重新准备全部流程。

### 反模式 3：dynamic_profile ❌

**实际代码（`agent.ts:125-130`）：**

```ts
const credits = Math.floor(Math.random() * 90) + 10;  // 随机 $10 ~ $99
return { role: 'user', content: `(session context) Account credits: $${credits}.` };
```

每轮在对话开头插入一条用户消息，内容是**随机生成的账户额度**：

```
第 1 轮：(session context) Account credits: $47.
第 2 轮：(session context) Account credits: $12.
第 3 轮：(session context) Account credits: $83.
```

**问题：额度是随机数，每轮都不同 → 前缀内容变了 → 缓存失效。**

**类比场景：** 想象一个客服系统，每轮对话前系统都会给用户账户余额贴一个变动标签。客服（Agent）每次看到的余额标签都不同，导致他每次都要重新理解整个对话上下文。

**大白话：** 就像快递单上的"包裹重量"每封邮件都不一样——邮局得重新算全部运费，不能复用之前的计算。

**为什么用"额度"这个例子？** 因为实际业务中确实有这类场景：用户订阅额度、剩余调用次数、账户余额等。这些值每轮都在变，如果塞进系统提示里，KV Cache 就废了。正确做法是把这些信息放在**最后一条消息**里，而不是塞进前缀。

### 反模式 4：sliding_window ❌

```
只保留最近 5 条对话 ← 之前的全丢掉！
```

**问题：上下文被截断 → 前缀变了 → 缓存失效，而且 Agent 丢了重要信息。**

大白话：就像看书只看最后一页，前面全忘了，不得不从头重读。

### 反模式 5：text_format ❌

```
把全部对话历史拼成一大段纯文本（不是结构化的 JSON）
```

**问题：纯文本格式每轮都不同（因为历史在增长）→ 缓存永远不命中。**

大白话：就像每次写总结都把之前的全文复制一遍再加新内容，文件越来越大，复印时间越来越长。

## 四、实验结果对比

```
Mode             总时间    缓存命中   说明
─────────────────────────────────────────────
correct              17s     53%    ✅ 前缀稳定，缓存命中
dynamic_system       29s      0%    ❌ 时间戳每轮变
shuffled_tools       35s      0%    ❌ 工具顺序每轮变
dynamic_profile      41s      0%    ❌ 额度每轮变
sliding_window       24s     59%    ⚠️ 有缓存但上下文丢失，多跑了几轮
text_format          59s     26%    ❌ 纯文本格式，缓存几乎不命中
```

### 最触目惊心的对比

- **correct** 17 秒 vs **text_format** 59 秒 = **3.5 倍差距**
- 只不过是把"结构化消息"换成了"纯文本拼接"

## 五、为什么"看似无害"的小改动破坏力这么大？

因为 KV Cache 的缓存粒度是**整个前缀**。

```
缓存键 = "系统提示 + 用户消息 + 助手历史" 的完整字符串
```

只要前缀中**任何一个字符**变了，整个缓存键就变了，全部重新计算。

```
correct:   "You are an assistant... find files" → 缓存 ✓
+timestamp: "You are an assistant... [2025-09-18] find files" → 缓存 ✗
```

哪怕只是加了一个时间戳，哪怕内容看起来"差不多"，缓存就废了。

### 对比：System Hint 为什么不会破坏 KV Cache？

对比 **KV Cache 的 `dynamic_system`** 和 **System Hint 实验（9.system-hint）**：

```
┌──────────────────────────────────────────────────────────────────┐
│  dynamic_system（KV Cache 反模式）                                   │
│                                                                      │
│  agent.ts:                                                              │
│  return `${SYSTEM_PROMPT}[generated_at: ${timestamp}]`;             │
│                                                                      │
│  → 时间戳写进 system prompt 本身                                       │
│  → system prompt 内容变了                                             │
│  → system prompt 的 KV 全部失效                                      │
│  → history 也包含这个变化                                             │
│                                                                      │
│  结果：整条前缀重新计算，缓存全失                                       │
├──────────────────────────────────────────────────────────────────┤
│  System Hint（9.system-hint，本实验）                                   │
│                                                                      │
│  agent.ts:                                                              │
│  const messages = [...history, { role: 'user', content: statusBar }];  │
│                                                                      │
│  → system prompt 内容不变（固定）                                       │
│  → history 不变（状态栏不写入 history）                                │
│  → 状态栏是末尾临时 user 消息                                         │
│                                                                      │
│  结果：前缀命中缓存，只有 ~200 token 状态栏新计算                       │
└──────────────────────────────────────────────────────────────────┘
```

**一句话总结：**

```
改 system prompt = 改旧元素 → 伤根基 → KV 全失
追加临时 user 消息 = 加新元素 → 加一层壳 → 只算新部分
```

```
messages 数组的变化：

dynamic_system： 改原有 system prompt 对象的 content
  [{ role: 'system', content: '旧内容' }]
  → [{ role: 'system', content: '新内容（含时间戳）' }]   ← 改旧

System Hint：    在 messages 末尾追加一条新 user 消息
  [...history, { role: 'system', content: '固定' }]
  → [...history, { role: 'system', content: '固定' }, { role: 'user', content: '状态栏' }]  ← 加新
```

| 做法 | 改了什么 | KV Cache 影响 | 历史是否被污染 |
|------|----------|--------------|---------------|
| dynamic_system | system prompt 内容变了 | 全部失效 | 是（时间戳成为历史） |
| System Hint | 末尾追加临时 user 消息 | 只算状态栏 | 否（用完即弃） |

### 为什么 system prompt 不能改？（Chat Template 的角度）

补充一个底层原理：为什么"改一个空格"就导致缓存全失？

```
API 消息 → Chat Template → 模型 Token 流

API:  { role: "system", content: "你是助手" }
        ↓ Chat Template 转换
Token: <|im_start|>system
你是助手
<|im_end|>

如果改一个字符：
API:  { role: "system", content: "你是助手!" }
        ↓ Chat Template 转换
Token: <|im_start|>system
你是助手!
<|im_end|>   ← "!" 改变了 token 序列
```

```
关键原理：

1. Chat Template 把 system 消息转换为固定 token 序列放在最前面
2. KV Cache 按 token 序列缓存——"你是助手"和"你是助手!"是不同的 token 序列
3. 一旦不同，第一个不同 token 之后的 KV 全部需要重新计算
4. 系统提示词越靠前，影响范围越大（可能整个前缀都要重算）
```

**结论：这不是"经验法则"，而是 Chat Template + KV Cache 机制的必然结果。**

## 六、核心结论（5 条）

| # | 结论 | 大白话 |
|---|------|--------|
| 1 | **前缀稳定至关重要** | 前面的话不能变，变了就得重算 |
| 2 | **顺序也重要** | 同样的内容换个顺序，缓存也废 |
| 3 | **前缀中避免动态元数据** | 时间戳、计数器、额度别塞进系统提示 |
| 4 | **使用结构化消息格式** | JSON 格式比纯文本更利于缓存 |
| 5 | **完整历史优于激进截断** | 截断虽然省缓存但丢了上下文，反而更慢 |

## 七、延伸思考

1. **为什么滑动窗口有缓存但仍然最慢？**
   - 缓存命中率高（59%），但 Agent 丢了前面的上下文
   - Agent 不得不多跑几轮来弥补信息丢失（6 轮 vs 4 轮）
   - 总时间反而更长

2. **实际开发中怎么避免这些问题？**
   - 系统提示固定不变（时间戳放最后）
   - 工具顺序固定
   - 用结构化消息格式，不要纯文本拼接
   - 不要随意截断历史

3. **KV Cache 命中 ≠ 模型回答更好**
   - 缓存只影响速度，不影响回答质量
   - 但反模式（如 sliding_window）会让模型"失忆"，回答质量下降

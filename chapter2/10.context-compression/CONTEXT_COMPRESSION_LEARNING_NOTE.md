# 上下文压缩策略 —— 教学笔记

> 本笔记对应实验 2-10（上下文压缩策略对比）。
> 核心目标：**理解"上下文窗口有限时，怎么压缩信息才能又省空间又不丢关键信息"。**

---

## 一、这个实验在干什么？

一句话：**模拟"上下文窗口快满了"时，怎么把大量信息塞进有限空间。**

场景：让你调研 8 位 OpenAI 联合创始人的当前职业归属。你需要抓取 8 个网页的内容。

问题：8 个网页原文太长（~8914 token），超过了预算窗口（8000 token）。

解决方案：**用不同方式压缩信息**。

```
8 个网页原文 = ~8914 token → 超预算 → 失败！

压缩后：
  combined:      ~211 token → 通过（但丢信息）
  context_aware: ~184 token → 通过且最省
  individual:    ~567 token → 通过且信息最全
  windowed:      ~1918 token → 通过但体积大
```

**本质：怎么在有限的空间里，装最多的有用信息。**

---

## 二、6 种策略

```
┌─────────────────────────────────────────────────────────────────┐
│  8 个网页原文（每页 ~1000 字）                                     │
│  总计 ~8914 token                                                │
│  预算限制 = 8000 token                                           │
└──────────────────────────┬──────────────────────────────────────┘
                           │
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
     ┌───────────┐  ┌───────────┐  ┌───────────┐
     │  不压缩    │  │  压缩      │  │  智能压缩  │
     │           │  │           │  │           │
     │ 原文进历史 │  │ 摘要进历史 │  │ 按需压缩   │
     │ 8914 tok  │  │ 121-1918   │  │ 184-201    │
     │ ❌ 溢出    │  │ tok ✓     │  │ tok ✓     │
     └───────────┘  └───────────┘  └───────────┘
```

### 策略一览

| 策略 | 做法 | 体积 | 信息 | 一句话 |
|------|------|------|------|--------|
| **no_compression** | 网页原文直接进上下文 | 8914 tok | 最多 | 不压缩 → 溢出失败 |
| **individual** | 每页单独摘要再拼接 | 567 tok | 8/8 全 | 每页都仔细总结 |
| **combined** | 全部页合并后一次摘要 | 211 tok | 3/8 | 全部混在一起总结 |
| **context_aware** | 结合研究问题做聚焦摘要 | 184 tok | 3/8 | 只保留与问题相关的 |
| **citations** | context_aware + 来源链接 | 201 tok | 8/8 | 聚焦 + 带来源 |
| **windowed** | 最近保留全文，更早压缩 | 1918 tok | 8/8 | 近期细节 + 远期压缩 |

---

## 三、压缩流程：先压缩，再塞入

所有压缩策略的通用流程：

```
第一步：抓取网页原文
  8 个网页 → 每页 ~1000 字 → 总计 ~8914 token

第二步：调用 LLM 做摘要（压缩）
  ┌─────────────────────────────────────────┐
  │  individual: 调 8 次 LLM，每页摘要 1 次  │
  │  combined:    调 1 次 LLM，全部合并摘要  │
  │  context_aware: 调 1 次 LLM，聚焦摘要   │
  └─────────────────────────────────────────┘

第三步：把压缩结果放进对话历史（替代原文）
  ┌─────────────────────────────────────────┐
  │  历史 = [用户问题][摘要1][摘要2]...[摘要N]│
  │  体积从 8914 tok → 184-567 tok          │
  └─────────────────────────────────────────┘
```

```
数据流：

原文（8914 tok）
    │
    ▼  第一步：LLM 摘要
压缩后文本（184-567 tok）
    │
    ▼  第二步：放进上下文
替换原文进入对话历史
    │
    ▼  第三步：模型基于压缩文本回答
✅ 成功（不溢出）
```

**关键理解：** 本质是花一次 LLM 调用的代价（摘要），换取后续上下文窗口的空间。相当于"先付钱请人瘦身，再把瘦身后的内容塞进背包"。

## 四、每种策略的大白话解释

### no_compression（不压缩）❌

**做法：** 8 个网页原文全部塞进去。

```
历史 = [用户问题][网页1原文][网页2原文]...[网页8原文]
体积 = 8914 token > 8000 预算 → ❌ 溢出失败
```

**大白话：** 就像把 8 本百科全书全部塞进一个只能装 7 本的背包。装不下。

---

### individual（逐页摘要）✅

**做法：** 每页单独用 LLM 摘要，再拼在一起。

```
历史 = [用户问题][摘要1][摘要2]...[摘要8]
体积 = 567 token ✓
信息 = 8/8 联创全保留
摘要调用 = 8 次
```

**大白话：** 每本书单独请人总结成 1 页笔记，然后把 8 页笔记拼在一起。信息全，但请了 8 次人。

**优点：** 信息最全（8/8）
**缺点：** 摘要调用多（8 次 LLM），token 略大

---

### combined（合并摘要）✅

**做法：** 8 页全部内容合在一起，一次性总结。

```
历史 = [用户问题][合并摘要：所有联创的总结]
体积 = 211 token ✓
信息 = 3/8
摘要调用 = 1 次
```

**大白话：** 把 8 本书摞在一起，让一个人一次性总结所有人。结果是"张三、李四、王五..."，但具体细节模糊了。

**优点：** 最省调用（1 次），体积最小
**缺点：** 丢信息（只保留 3/8 人名），每页细节没了

---

### context_aware（结合问题聚焦）✅

**做法：** 摘要时结合"研究问题"（谁是目前联创？），只保留相关答案。

```
历史 = [用户问题][聚焦摘要：只保留与"当前职业"相关的信息]
体积 = 184 token ✓
信息 = 3/8
摘要调用 = 1 次
```

**大白话：** 告诉摘要人"你只需要回答一个问题：这些人现在在干什么？"其他无关内容全部不要。

**优点：** token 最省（184），最聚焦
**缺点：** 可能丢细节（只保留 3/8 人名）

---

### citations（聚焦 + 来源链接）✅

**做法：** context_aware 基础上，加上来源链接。

```
历史 = [用户问题][聚焦摘要 + 来源链接]
体积 = 201 token ✓
信息 = 8/8
摘要调用 = 1 次
```

**大白话：** 和 context_aware 一样聚焦，但加上"这是从哪来的"（来源链接）。方便后续追问。

**优点：** 信息全（8/8）+ 可追溯
**缺点：** 体积略大（201 vs 184）

---

### windowed（滑动窗口）✅

**做法：** 最近的内容保留全文，更早的压缩。

```
历史 = [用户问题][压缩的早期摘要][最近的全文]
体积 = 1918 token ✓
信息 = 8/8
摘要调用 = 7 次
```

**大白话：** 重要的近期内容保留完整，早期的只保留摘要。像翻书一样，最近看的保留细节，之前的只看目录。

**优点：** 信息全（8/8），适合长对话
**缺点：** 体积最大（1918 tok），摘要调用多（7 次）

---

### 6 种策略压缩方式一览

| 策略 | 原文怎么处理 | 压缩结果进历史 | 摘要调用 | 体积 | 信息 |
|------|-------------|---------------|----------|------|------|
| no_compression | 原文不进压缩 | 8914 tok 原文 | 0 | 8914 | 最多 |
| individual | 每页单独摘要 | [摘要1][摘要2]...[摘要8] | 8 次 | 567 | 8/8 |
| combined | 全部合并后摘要 | [合并摘要] | 1 次 | 211 | 3/8 |
| context_aware | 结合问题聚焦摘要 | [聚焦摘要] | 1 次 | 184 | 3/8 |
| citations | 聚焦摘要 + 来源链接 | [摘要 + 链接] | 1 次 | 201 | 8/8 |
| windowed | 近期保留全文+早期压缩 | [压缩早期][最近全文] | 7 次 | 1918 | 8/8 |

| # | 结论 | 一句话 |
|---|------|--------|
| 1 | **无压缩必然溢出** | 上下文管理是 Agent 的刚需 |
| 2 | **context_aware 最省** | 结合查询聚焦，只留相关信息 |
| 3 | **强压缩有信息代价** | combined 只保留 3/8 人名 |
| 4 | **windowed 适合长对话** | 近期细节 + 远期压缩的折中 |
| 5 | **摘要调用也是成本** | individual 8 次 vs combined 1 次 |

### 位置偏好（Position Bias）：为什么 windowed 有效？

模型不是均匀地关注上下文中的所有位置。研究发现：

```
模型注意力分布：
开头 ████████████████████████████ 高 ← 关键信息放这里
中间 ████████                     低 ← 容易被忽视
结尾 ██████████████████           高 ← 关键信息放这里
```

**含义：**
- 模型对**开头**（system prompt）和**结尾**（最新消息）分配更多注意力
- **中间**部分更容易被"遗忘"
- 所以关键信息应该放在开头或结尾，不要塞在中间

**对 windowed 策略的解释：**
- windowed 保留最近一次全文在**末尾** → 模型注意力高 → 效果好
- 更早的历史压缩后放在**中间** → 模型注意力低 → 但已经压缩了，体积小
- 这不是巧合，而是利用了模型的位置偏好

## 六、延伸思考

### 1. 为什么 combined 和 context_aware 都是 3/8？

因为它们都是"合并后一次性摘要"。模型在总结时，只抓住了部分联创的名字。individual 是逐页总结，每页都独立，所以 8/8 全。

### 2. windowed 为什么体积最大？

因为它保留了最近一次的全文（约 1000 字 × 1 次）。虽然更早的压缩了，但最近一次的全文本身就很大。

### 3. 实际怎么选？

```
场景判断：

信息全 > 一切 → individual 或 citations
体积最省 > 一切 → context_aware
需要后续追问 → citations
长对话多轮 → windowed
简单任务 → combined（1 次调用搞定）
```

### 4. 和前面实验的关系？

| 实验 | 解决什么问题 |
|------|-------------|
| KV Cache（2-3） | 缓存中间计算结果，加速推理 |
| System Hint（2-9） | 临时注入状态，引导行为 |
| **上下文压缩（2-10）** | **压缩信息本身，适配窗口大小** |
| 渐进式披露（2-6） | 按需加载技能 |

**本质：** Agent 的上下文管理贯穿所有实验：
- 怎么**加速**（KV Cache）
- 怎么**引导**（System Hint）
- 怎么**压缩**（本实验）
- 怎么**加载**（渐进式披露）

# 14.conversational-ui 教学笔记：可见产物是最好的验收

官方阅读顺序第 3 步：把 Starter 的循环用于可见产物，检查"代码变化是否满足用户需求"。本实验是 0.coding-agent 的直接后继——同样的"改源码→验证"，验收从"测试通过"换成"构建通过 + 内容断言"。

## 一、整文件改写比零散 edit 更适合小模型

官方用 `apply_edits`（返回文件全文）而不用 search/replace，原因实测可感：小模型逐字复制 oldText 经常差一个空格导致零命中（0.coding-agent 里吃过亏）。整文件改写把"定位"和"改写"合成一步，对小文件更稳定。本实验 T1 的 diff 证明它能做到最小改动：一行 `background`，别处不动。

代价是 token：文件越大越贵。生产级做法是两者并存（小文件全文、大文件补丁），本实验只演示前者。

## 二、白名单是"执行边界"的最小形态

`EDITABLE_FILES = [App.jsx, theme.css]` 两行配置就是书里"Agent 能碰什么不能碰什么"的全部落地。sanitize 三层：形状不对的丢弃（防 KeyError 中断整轮，官方测试文件专门测这三类畸形）、路径出白名单抛错、空内容丢弃。

## 三、"其他不动"是最难的断言

T1 需求里"其他不动"无法全量断言，只能抽查：T2 用 mustNot 查旧文案残留，T3 用 mustNot 查旧字号残留。教训：自然语言里的否定约束（别碰 X），要翻译成"X 的旧值必须消失 + 新值出现"两条正向检查。diff 行级展示是给人看的第二道网。

## 四、构建是 UI 任务的客观裁判

`vite build` 270ms 跑完，JSX 语法错、import 写错立刻现形。和 5-4 的 solver、5-10 的测试是同一角色：机器说了算，不听模型自称"改好了"。三个任务全部一次过、build 全绿——可见产物的循环比开放式生成稳，因为"长什么样"有编译器兜底。

## 实测（gemma4，Ollama 本地）

- T1 按钮变蓝：尝试 1，断言 ✓ + build ✓，diff 仅 1 行
- T2 改标题文案：尝试 1，断言 ✓ + build ✓（只改 App.jsx）
- T3 标题放大：尝试 1，断言 ✓ + build ✓（只改 theme.css）

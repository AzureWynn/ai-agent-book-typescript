# 15.permission-objects 教学笔记：生成自由，执行不自由

官方 5-15 本地版：SQLite 替代 PG（无行级安全与并发语义，思想一致，如实声明）。招聘场景一比一复刻 + 模型生成操作批 + 8 项固定攻击。

## 一、A组是最好的故事：模型好心办坏事，数据层兜底

请求"把 Bob（期望薪资50万）录进来"，模型照办生成 create 操作——应用层看不出毛病。数据层按职位薪资带一算：500000 超出 80000-150000，REJECT。同一批里合法的 Alice 推进照常 ACCEPT。**生成侧不用完美，执行侧必须完美**——这就是权限内嵌要解决的错位：模型负责"想干什么"，数据层负责"允不允许"。

## 二、六层检查的顺序就是攻击面的顺序

租户隔离 → 角色权限 → 状态机 → 跨字段校验 → 引用完整性 → 受控反应。8 项攻击每项恰好撞上一层：
- hired→applied 回退被状态机拦（终态无出边）
- 跨租户建档被引用完整性拦（other-org 下没有 position#1 可引）——注意不是租户检查直接拦的，跨租对象连被引用的资格都没有，这是纵深
- 未知类型、读不存在对象都是 Validation 先行，权限错误只占 1/8

## 三、反应（reaction）是"受控后果"的最小形态

hired 落定自动 queued 一条 offer-letter 进 reaction log——副作用不禁止，但必须走数据层登记、可审计。对比 5-4 执行工具的"危险动作审批"：那边是事前拦，这边是事后留痕，两招并用才是完整。

## 四、SQLite 换 PG 丢了什么

丢的是行级安全策略、并发事务语义、多租户 schema 隔离——生产级必备，教学可空。本实验的六层检查全是应用侧逻辑，不依赖 PG 特性，所以降级不伤课。但 README 里写清：结论限"权限内嵌思想"，PG 工程结论以官方为准。

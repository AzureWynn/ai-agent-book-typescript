# 11.log-diagnosis 教学笔记：诊断看眼力，用例看手艺

官方 5-11 本地版：确定性 SUT（buggy/fixed 双版本）+ 模型两调（诊断→用例）+ 重放翻转 + Issue 草稿投递。MCP 提 Issue 换成本地草稿，诊断三件套一分没少。

## 一、诊断 4/4 命中：模型眼力可以

S1 抓 R1（缺前置校验）+R2（误报成功），S2 抓 R3（8300ms>5000ms 无降级，证据数字都对），S3 抓 R1。三个场景、四个真问题全中，优先级模块 PRD 引用全对。**读轨迹找偏离是小模型干得好的活**——证据都在文本里，不用推理跳跃。

## 二、臆造出在 S3：退款流程"必须查库存"

S3 正常退款轨迹里根本没有 inventory 的事，模型却报 P2"退款流程必须包含库存查询"，还配了 RT-002——PRD 和架构里都没这条。buggy/fixed 双挂，无翻转。**"只报告确有证据的问题"这句写进 prompt 也拦不住加戏**，凡是"流程完整性"类联想都是臆造高发区。对策：诊断门禁加一条"每个问题必须引用轨迹原文轮次号"，本实验没做，留作练习。

## 三、用例是手艺活：S2 的 param 格式错

S2 诊断完美，用例 `step_present` 的 tool 却填了 `inventory_service.check_stock`（模块.工具格式），DSL 要的是 `check_stock`——类型合法、参数格式错，双臂都"缺失"，无翻转。和 5-2 的"合法≠正确"同构：**断言 DSL 的类型校验拦不住参数语义错**，得给模型看一个完整例子（few-shot），光给类型说明不够。

## 四、翻转才是回归测试的及格线

RT-001（S1/S3）FAIL→PASS 翻转 ✓：同一输入，buggy 挂、fixed 过——这条用例锁死了 bug。
RT-002（S1，final_status_is failed）：buggy 挂得对，但 fixed 的 success 是合法成功（重试后真退了），fixed 也挂——模型把"修复后应成功"写成了"应失败"。**期望写错的用例比没用例更坏**：它会把修好的系统也判错。

## 实测（gemma4，Ollama 本地）

- S1：诊断 2/2，用例 2 条，翻转 1/2
- S2：诊断 1/1，用例 1 条，翻转 0/1（param 格式错）
- S3：诊断 1/1+1 臆造，用例 2 条，翻转 1/2

# 6.4 实时语音链路（简化教学版）

> 本章是 6-1~6-3「时序三连」的模态补全：前面扩的是**何时被唤醒、怎么异步**，这里扩的是**怎么听见、怎么说话**。

## 一、降级点先说清，别把简化版当官方复现

| 环节 | 官方 6-5/6-6 | 本实验 | 差异影响 |
| --- | --- | --- | --- |
| ASR | Qwen2-Audio / MiniCPM-o（原生音频模型） | faster-whisper tiny（CPU int8） | 识别率低、输出可能繁体（`天氣` vs `天气`），不影响语义 |
| TTS | 云端 Fish Audio 等 | macOS `say` 系统音色 | 音质机械，无情感韵律 |
| 对话 | 端到端语音模型 | ASR → 文本 LLM → TTS（级联） | 无端到端延迟优化，轮次间有静默 |

结论只能说到"**级联语音闭环在本机跑得通**"，说不到"语音交互质量达标"。这是 5-8（合成素材）、5-9（跳过 diffusion 臂）同样的诚实边界。

## 二、真正值得学的：模态扩展的三笔额外成本

换成语音之后，每一轮多了三笔账，5-x 章节完全不用付：

1. **序列化成本**：16kHz 单声道，5 秒 = 160KB。文本瞬时，音频按采样率累积。
2. **识别误差要转成语义误差处理**：`今天天氣怎麼樣` 是繁体的，但语义没错。如果下游要按关键词匹配（离线臂的 `天气` 正则），就得做繁简归一——这是**工程债**，不是模型问题。
3. **合成有时长**：`say` 出 3.66s 音频，用户要听完。文本回复是"即读即走"，语音回复必须考虑播报长度上限（我们的 prompt 限 30 字就是为此）。

## 三、`say` 救了这个实验：零外部依赖的 TTS

macOS 自带 9 个中文音色（`say -v '?' | grep zh_CN`），官方 10-6 狼人杀也用它。好处是整个语音链路**没有一个外部 API 依赖**——ASR 本地、TTS 系统、LLM 是 Ollama。代价是只能在 macOS 跑，这点如实标在注意事项里。

音色选择还有个小坑：并非所有音色都支持 `LEF32@22050` 输出格式，不支持时 `say` 会失败，得退回默认格式重试一次（代码里已处理）。

## 四、两个真坑

**PyAV 版本冲突**：faster-whisper 1.2.1 调用 `av.open(..., metadata_errors=...)`，而 PyAV 19 已移除该参数，报 `TypeError: open() got an unexpected keyword argument`。解法是钉住 `av<19`。`npm run setup` 现在会检测并提示。

**snake_case 穿透边界**：Python 侧输出 `load_ms`/`infer_ms`，TS 接口写的是 `loadMs`/`inferMs`，`JSON.parse` 不做转换，耗时直接显示 `NaN`。这类 bug 不报错、只让数字消失，比崩溃更难查——凡是跨语言边界传结构体，都要显式映射。

## 五、离线臂的价值：把"机制"与"模型能力"分开

离线臂的应答走确定性模板（`offlineReply`），不调模型。这样 ASR/TTS 链路可以在没有任何模型的情况下验证，`npm run eval` 里 LLM 那一列显示 0ms 就是标记。模板命中不了的句子会走兜底反问，与 5-5（代码化规则）的思路一致：**机制先跑通，再谈智能**。

## 实测（faster-whisper tiny + gemma4 + macOS say，本机）

| 臂 | ASR 文本 | 回复 | ASR | LLM | TTS |
| --- | --- | --- | --- | --- | --- |
